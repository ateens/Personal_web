# SYGMA 가계부 기능 설계

- 상태: 구현 기준안
- 작성일: 2026-07-24
- 대상: 기존 SYGMA 웹 앱에 추가할 단일 사용자용 가계부
- 구현 상태: Phase 0 보안 경계와 Phase 1~3 수동 입력 MVP 구현 완료

## 1. 결론

가계부는 전역 내비게이션의 `가계부` 항목과 전용 주소 `/finance`를 가진 별도 화면으로 만든다. 기존 SYGMA 셸과 동기화 상태는 재사용하되, 가계부 안에서는 전용 월 헤더와 5개 내부 탭을 사용한다.

금액 계산은 완전한 복식부기 엔진 대신 아래 세 기록을 분리하고 연결한다.

1. `entry`: 무엇을 언제 사용하거나 벌었는가
2. `movement`: 어느 계좌에서 돈이 실제로 언제 움직였는가
3. `settlement`: 예정된 납부와 실제 돈 이동이 무엇을 처리했는가

이 구조로 신용카드 사용과 카드대금 출금, 대출 원금과 이자, 비용 귀속월과 실제 납부월을 중복 없이 계산한다.

일반 운영 앱은 애플리케이션 인증이 없고 익명 `/api/state` 읽기·쓰기가 가능하다. 따라서 실제 금융 데이터는 기존 `state`, `/api/state`, 일반 IndexedDB에 저장하지 않는다. Phase 0에서 구현한 가계부 전용 로그인, 세션, `/api/finance/state`, `finance_state`, `finance_state_history` 경계 안에서만 금융 데이터를 다룬다.

## 2. 목표

- 은행·현금성 계좌의 현재 잔액과 계좌별 흐름 관리
- 수입, 소비, 환불, 계좌 이체 관리
- 체크카드, 신용카드, 현금, 계좌이체, 기타 결제수단 관리
- 신용카드 사용일, 청구 확정, 출금 예정, 실제 출금을 분리
- 대출 원금, 이자, 수수료, 실제 납부를 분리
- 고정비의 비용 귀속월과 실제 출금일을 분리
- 카드대금·대출·고정비를 함께 보는 결제 예정 캘린더
- 사용 기준, 실제 출금 기준, 예정 기준의 독립 통계
- 월이 바뀌어도 같은 소비가 두 번 집계되지 않는 계산

## 3. 1차 범위에서 하지 않는 것

- 은행·카드사 자동 연동
- 문자, 영수증 OCR, 메일 자동 수집
- 투자자산, 세금, 다중 통화
- 가족·다중 사용자 공유
- AI 자동 분류
- 카드 혜택·포인트 최적화
- 복잡한 변동금리 상환표 자동 계산
- 카드사별 영업일·공휴일 이동 자동화
- 기존 전역 Calendar와 즉시 통합

초기 버전은 수동 입력을 정확히 관리하는 데 집중한다. 외부 자료 가져오기는 JSON 백업 검증 후 별도 단계로 둔다.

## 4. 사용자에게 보여 줄 날짜 이름

`결제일`은 카드 사용일과 카드대금 납부일 양쪽 의미로 쓰일 수 있으므로 UI에서 단독으로 사용하지 않는다.

| 화면 용어 | 의미 | 저장 값 |
|---|---|---|
| 사용일 | 물건이나 서비스를 사용한 날 | `occurredOn` |
| 확정일 | 금액이 더 이상 예상이 아닌 것으로 바뀐 날 | `confirmedOn` |
| 명세서 확정일 | 카드 청구 금액이 확정된 날 | `statementOn` |
| 출금 예정일 | 계좌에서 빠질 예정인 날 | `scheduledOn` |
| 실제 출금일 | 계좌 잔액이 실제로 바뀐 날 | `postedOn` |

모든 금융 날짜는 `YYYY-MM-DD`로 저장한다. 내부 월 통계 키 `recognitionMonth`는 사용일·발생일·납부 예정일에서 자동 생성하며 사용자가 직접 입력하지 않는다. 작성 시각은 ISO timestamp로 따로 저장한다. 월 통계는 Asia/Seoul의 날짜 경계를 사용한다.

## 5. 절대 섞지 않는 계산

### 5.1 이번 달 쓴 돈

선택 월이 `recognitionMonth`인 소비와 대출 이자·수수료의 합에서 환불을 뺀다.

- 신용카드 구매는 사용한 달에 한 번만 포함
- 카드대금 출금은 다시 포함하지 않음
- 대출 원금 상환은 포함하지 않음
- 대출 이자와 수수료는 포함
- 내 계좌끼리 이동은 포함하지 않음
- 잔액 조정은 포함하지 않음

### 5.2 이번 달 실제로 빠진 돈

`postedOn`이 선택 월인 외부 출금의 합이다.

- 신용카드 대금 포함
- 대출 원금·이자·수수료 납부 포함
- 체크카드·현금·계좌 직접 지출 포함
- 내 계좌끼리 이동은 전체 가계 기준에서 제외
- 잔액 조정은 제외

### 5.3 앞으로 빠져나갈 돈

선택 기간 안에 `scheduledOn`이 있고 아직 실제 `movement`가 연결되지 않은 금액의 합이다.

- 예상, 확정, 연체를 상태별로 구분
- 예상 금액은 현재 잔액을 바꾸지 않음
- 예정일이 지났지만 실제 출금이 없으면 `연체/미확인`을 계산

### 5.4 잔액과 부채

```text
계좌 잔액 = 시작 잔액 + 실제 입금 - 실제 출금 + 잔액 조정
카드 미납액 = 청구 대상 금액 + 수수료 - 환불 - 납부액
대출 잔액 = 시작 원금 + 추가 대출 - 상환 원금
```

계좌 잔액과 부채는 저장된 합계 필드를 믿지 않고 원본 기록에서 계산한다.

## 6. 필수 시나리오

| 상황 | 사용 통계 | 예정 통계 | 실제 출금 통계 |
|---|---:|---:|---:|
| 1월 31일 카드 120,000원 사용, 3월 5일 출금 | 1월 +120,000 | 3월 +120,000 | 실제 출금된 3월 +120,000 |
| 7월 전기료 80,000원을 8월 15일 납부 | 7월 +80,000 | 8월 +80,000 | 실제 납부월 +80,000 |
| 대출 550,000원 납부: 원금 500,000, 이자 50,000 | 이자 +50,000 | 550,000 | 550,000, 대출 잔액 -500,000 |
| 내 통장 A에서 B로 1,000,000원 이동 | 0 | 0 | 전체 가계 기준 0 |
| 1,200,000원을 12개월 할부 구매 | 구매월 +1,200,000 | 매월 100,000 | 매월 실제 출금 100,000 |
| 카드 구매가 다음 달 환불됨 | 환불월에 마이너스 소비 | 다음 청구액 감소 | 실제 현금 입금이 없으면 입금 0 |

환불은 과거 구매 금액을 덮어쓰지 않는다. 원거래에 연결된 반대 기록으로 남기며 기본 통계에서는 환불이 발생한 달에 반영한다.

## 7. 데이터 모델

### 7.1 저장 루트

```js
{
  schemaVersion: 1,
  currency: "KRW",
  accounts: [],
  paymentMethods: [],
  entries: [],
  movements: [],
  settlements: [],
  cardStatements: [],
  loans: [],
  loanPayments: [],
  recurringRules: [],
  balanceChecks: []
}
```

모든 금액은 원 단위의 안전한 정수로 저장한다. 음수 금액으로 방향을 표현하지 않고 `kind`와 출발·도착으로 의미를 정한다.

### 7.2 계좌 `accounts`

```js
{
  id,
  name,
  type: "bank" | "cash" | "e_money",
  institution,
  openingBalanceKrw,
  openingOn
}
```

- 계좌번호는 일부라도 저장하지 않는다.
- `openingBalanceKrw`는 `openingOn` 당일 거래가 시작되기 직전 잔액이다.
- 잔액에는 `openingOn <= postedOn <= 조회일`인 확정 이동만 반영한다.
- 현재 잔액은 저장하지 않고 시작 잔액과 실제 `movement`로 계산한다.

### 7.3 결제수단 `paymentMethods`

```js
{
  id,
  name,
  type: "debit_card" | "credit_card" | "cash" | "bank_transfer" | "other",
  linkedAccountId,
  paymentAccountId,
  cycleEndDay,
  dueDay,
  dueMonthOffset
}
```

- 체크카드는 `linkedAccountId`에서 즉시 출금되는 것이 기본값이다.
- 신용카드는 `paymentAccountId`와 청구 주기 템플릿을 가진다.
- 카드 주기 템플릿 결과는 항상 `예상`이며 실제 명세서로 확정할 수 있다.
- 카드번호는 일부라도 저장하지 않으며 CVC, 인터넷뱅킹 정보도 저장하지 않는다.

### 7.4 사용·수입 기록 `entries`

```js
{
  id,
  kind: "expense" | "income" | "refund",
  title,
  amountKrw,
  occurredOn,
  recognitionMonth,
  confirmedOn,
  category,
  paymentMethodId,
  originalEntryId,
  recurringRuleId,
  periodKey,
  status: "draft" | "confirmed" | "void",
  note,
  createdAt,
  updatedAt
}
```

- 할부 구매도 원래 구매는 한 건이며 전체 금액을 구매월에 한 번만 센다.
- 취소·환불은 `originalEntryId`로 원거래를 연결한다.
- 확정된 기록은 삭제하지 않고 `void`와 정정 기록으로 남긴다.

### 7.5 실제 계좌 이동 `movements`

```js
{
  id,
  kind: "external" | "transfer" | "card_payment" | "loan_payment" | "adjustment",
  amountKrw,
  postedOn,
  fromAccountId,
  toAccountId,
  counterpartyType: "external" | "card" | "loan" | "adjustment",
  counterpartyId,
  status: "confirmed" | "void",
  note,
  createdAt,
  updatedAt
}
```

- 외부 입출금·카드대금·대출납부는 `fromAccountId`와 `toAccountId` 중 정확히 하나만 가진다.
- 둘 다 내 계좌인 기록은 반드시 `transfer`이며 수입·소비·전체 실제 출금 통계에서 제외한다.
- 예정 금액은 `movement`를 만들지 않는다.

### 7.6 예정과 실제 연결 `settlements`

```js
{
  id,
  targetType: "entry" | "card_statement" | "loan_payment",
  targetId,
  expectedAmountKrw,
  scheduledOn,
  movementId,
  settledAmountKrw,
  status: "estimated" | "confirmed" | "paid" | "canceled",
  createdAt,
  updatedAt
}
```

- 한 실제 출금이 여러 사용 기록을 처리할 수 있다.
- 한 사용 기록이 할부·부분 납부로 여러 `settlement`를 가질 수 있다.
- 같은 `movementId`에 연결된 `settledAmountKrw` 합은 실제 이동 금액과 같아야 한다.

### 7.7 카드 명세서 `cardStatements`

```js
{
  id,
  paymentMethodId,
  periodStart,
  periodEnd,
  statementOn,
  scheduledOn,
  statementAmountKrw,
  status: "estimated" | "confirmed" | "paid",
  items: [
    {
      entryId,
      amountKrw,
      installmentNumber,
      installmentCount
    }
  ],
  createdAt,
  updatedAt
}
```

- 구매 합계, 환불, 수수료와 명세서 금액의 차이를 표시한다.
- 명세서를 `confirmed`로 바꾼 뒤에도 실제 출금 전까지 계좌 잔액은 바뀌지 않는다.
- 실제 납부는 `settlement`와 `movement`로 연결한다.

### 7.8 대출과 대출 납부

```js
{
  id,
  name,
  lender,
  openedOn,
  openingPrincipalKrw,
  termMonths, // 실제 원금을 갚는 개월 수
  graceMonths,
  scheduleMode: "auto" | "manual",
  paymentAccountId,
  annualRate,
  archivedAt
}
```

```js
{
  id,
  loanId,
  dueOn,
  paidOn,
  recognitionMonth,
  principalKrw,
  interestKrw,
  feeKrw,
  movementId,
  status: "estimated" | "confirmed" | "paid" | "canceled",
  createdAt,
  updatedAt
}
```

- `principalKrw + interestKrw + feeKrw`는 실제 납부 금액과 같아야 한다.
- 원금만 대출 잔액을 줄인다.
- 이자와 수수료만 사용 통계에 포함한다.
- 전체 월별 계획은 기존 `loanPayments`와 `settlements`에 저장하며, 거치 기간과 상환 기간의 합은 최대 1,200개월이다.
- 자동 계산은 거치 기간 동안 이자만 반영하고 이후 원리금균등으로 계산한다. 마지막 달 원금은 반올림 잔액을 전액 반영한다.
- 수동 입력은 각 달의 원금과 이자를 직접 저장하며, 전체 원금 합계가 시작 원금과 정확히 같아야 한다.
- 계약 계획과 실제 청구가 다르면 실제 출금 확인 단계에서 금액을 수정한다.
- `scheduleMode`가 없는 과거 대출의 `monthlyPaymentKrw`는 기존 계약 참고값으로 계속 읽는다.

### 7.9 반복 일정 `recurringRules`

```js
{
  id,
  kind: "fixed_expense" | "fixed_income" | "loan_payment",
  name,
  amountEstimateKrw,
  dueDay,
  paymentMethodId,
  accountId,
  loanId,
  activeFrom,
  activeUntil,
  status: "active" | "paused" | "archived"
}
```

- 규칙 자체는 실제 소비나 실제 출금이 아니다.
- 화면에서는 미래 예정으로 계산하되, 사용자가 확정하거나 실제 납부하면 해당 월의 기록을 만든다.
- 생성 키는 `ruleId + periodKey`로 고정해 같은 월 기록이 중복 생성되지 않게 한다.
- 29~31일은 해당 월의 마지막 날로 줄인다.
- 고정비는 출금 예정 월의 비용으로 기록한다.
- 공휴일 이동은 자동 추측하지 않고 사용자가 실제 예정일을 고친다.
- 한 달의 실제 금액을 고쳐도 다음 달 규칙은 바뀌지 않는다.

### 7.10 잔액 확인 `balanceChecks`

```js
{
  id,
  accountId,
  checkedOn,
  calculatedBalanceKrw,
  actualBalanceKrw,
  adjustmentMovementId,
  createdAt
}
```

잔액 차이를 조용히 덮어쓰지 않는다. 확인값과 계산값의 차이를 보여 준 뒤 사용자가 승인한 경우에만 `adjustment` 이동을 만든다. 조정 금액은 수입·소비·현금흐름 통계에서 제외한다.

## 8. 불변조건과 검증

서버 저장 전에 다음을 검사한다.

- 모든 금액은 `0`보다 큰 안전한 정수
- 날짜와 월 형식 유효
- 모든 ID 유일
- 참조하는 계좌, 결제수단, 거래, 카드, 대출이 존재
- 자기 계좌로 보내는 이체 금지
- 실제 이동 한 건의 연결 금액 합이 실제 이동 금액과 일치
- 대출 납부의 원금·이자·수수료 합이 실제 납부액과 일치
- 카드 할부 회차 합이 환불 반영 후 구매 총액과 일치
- 같은 반복 규칙과 대상 월 조합은 한 번만 존재
- `paid` 상태에는 실제 `movementId`가 필요
- `estimated` 상태는 계좌 잔액을 바꾸지 않음
- 카드대금 납부, 대출 원금, 내부 이체를 소비 통계에서 제외
- 확정 카드 명세서는 금액·예정일이 같은 활성 `settlement`를 정확히 하나 가짐
- 명세서에 묶인 카드 사용의 기존 직접 예정은 `canceled`로 바뀜
- 납부 완료 대출은 날짜·금액·계좌가 일치하는 전용 이동과 정산을 정확히 하나 가짐
- 누적 상환 원금은 시작 원금을 넘지 않음
- 잔액 차이는 정확히 그 차이만큼의 전용 `adjustment`로만 보정

금융기관 정정·소급 처리 때문에 날짜 순서가 일반적이지 않은 기록은 무조건 거부하지 않는다. 저장 전 경고하고 사용자가 확인하면 허용한다.

## 9. 보안과 저장 경계

### 9.1 현재 상태

- 운영 Railway 앱에는 애플리케이션 로그인이나 사용자 구분이 없다.
- 익명 사용자가 `/api/state`와 Google Calendar 읽기 API에 접근할 수 있다.
- 리비전 검사, Origin 검사, rate limit은 인증이 아니다.
- 기존 전체 상태는 PostgreSQL과 브라우저 IndexedDB에 저장된다.

따라서 금융 데이터는 기존 전역 상태에 추가하지 않는다.

### 9.2 선택한 MVP 저장 방식

완전한 금융기관별 SQL 스키마를 먼저 만들지 않고, 아래처럼 별도 JSONB 상태를 사용한다.

```text
finance_state
  id
  state jsonb
  revision
  updated_at

finance_state_history
  id
  finance_state_id
  source_revision
  state jsonb
  created_at
```

- 전용 `/api/finance/state`만 금융 상태를 읽고 쓴다.
- 모든 금융 API는 단일 소유자 세션을 요구한다.
- `If-Match` 또는 `baseRevision`이 맞지 않으면 `409`로 거부한다.
- 성공한 변경 전 상태를 `finance_state_history`에 남긴다.
- 기존 `/api/state` 응답과 브라우저 일반 IndexedDB에는 금융 데이터가 절대 포함되지 않는다.
- MVP 가계부는 온라인 전용으로 시작하며 로그아웃 시 메모리의 금융 상태를 지운다.

이 방식은 현재의 단일 사용자·수동 입력 규모에서 가장 작은 안전 경계다. 자동 수입이나 거래 수가 커져 전체 상태 저장 지연이 눈에 띄면 개별 거래 테이블과 record-level API로 옮긴다.

### 9.3 인증 최소 요구

- 서버 환경변수에는 평문 비밀번호가 아니라 `scrypt` 해시와 별도 session secret 저장
- 로그인 rate limit
- `HttpOnly`, `Secure`, `SameSite=Strict` 세션 쿠키
- 세션 만료와 명시적 로그아웃
- 금융 API 전체에 서버 측 권한 검사
- 로그인되지 않은 읽기·쓰기 모두 `401`
- 전체 계좌번호, 카드번호, CVC, 은행 비밀번호, 인증서 저장 금지
- 로그와 오류 응답에 금액·메모·금융 상태 본문 기록 금지

기존 공개 앱 전체를 비공개로 바꾸지 않고 `/finance` 데이터 경계만 잠그는 것이 기본안이다. 사용자가 전체 앱 비공개 전환을 원하면 별도 결정으로 처리한다.

### 9.4 로컬 `budget/` 파일

현재 저장소의 `budget/*.xlsx`는 Git에 추적되지 않고 현재 빌드 산출물에도 포함되지 않는다. 실제 값은 이번 설계에서 읽지 않았다. 구현 전에 해당 경로를 Git 무시 목록에 넣고, 향후 가져오기는 브라우저에서 사용자가 선택한 파일을 일회성으로 파싱하는 별도 단계로 진행한다.

## 10. 화면 구조

### 10.1 전역 진입

- 사이드바 마지막에 `가계부 ₩`
- 전용 주소 `/finance`
- 가계부는 다른 관리 화면의 내부 탭이 아닌 독립 화면으로 연결
- 기존 11개 Option 내비게이션 단축키는 그대로 유지하고 가계부는 우선 단축키 없음
- 새 HTML 문서나 라우터 라이브러리 없이 기존 SPA fallback 재사용
- `/finance` 직접 접속, 새로고침, 뒤로가기를 지원

### 10.2 가계부 전용 상단

가계부에서는 전역 빠른 할 일 입력창과 FAB를 숨기고 아래만 표시한다.

```text
가계부        ‹ 2026년 7월 ›        잠그기
현황 | 내역 | 결제 예정 | 관리 | 통계
```

기존 사이드바와 모바일 메뉴 버튼은 유지한다. 별도 하단 내비게이션이나 두 번째 FAB는 만들지 않는다. 기록 추가는 `내역` 탭의 네이티브 펼침 폼으로 제공한다.

### 10.3 현황

상단 숫자는 네 개만 둔다.

1. 현재 은행 잔액
2. 이번 달 쓴 돈
3. 이번 달 실제로 빠진 돈
4. 앞으로 30일간 빠질 돈

그 아래에는 다음만 둔다.

- 월을 넘기는 카드·고정비 안내
- 가까운 출금 일정
- 계좌별 잔액
- 카드별 다음 납부액
- 다음 대출·고정비
- 명세서 차이, 미확인 출금, 잔액 불일치처럼 행동이 필요한 경고

`예정 반영 후 잔액`에는 항상 `예상` 표시를 붙인다.

### 10.4 내역

기본 목록은 서로 다른 기록을 한 표에 강제로 섞지 않는다.

```text
[쓴 돈] [계좌 입출금] [예정]
```

데스크톱:

```text
사용일 | 내용 | 수단 | 금액 | 실제·예정 출금일 | 상태
```

모바일은 표를 축소하지 않고 항목 카드로 바꾼다. 신용카드 행에는 두 시점을 함께 표시한다.

```text
카페 48,000원 · 신용카드
[사용 7/24] → [출금 예정 8/14]
7월 쓴 돈에 포함 · 8월 실제 출금 예정
```

### 10.5 결제 예정

- 달력에는 모든 카드 사용 건이 아니라 계좌에서 빠질 일정만 표시
- 한 날짜에는 총액과 예상·확정·완료 상태를 먼저 표시
- 날짜를 선택하면 아래 목록에서 카드대금, 고정비, 대출 원금·이자를 상세 표시
- 색만 사용하지 않고 `카드`, `고정비`, `원금`, `이자` 텍스트와 아이콘 병행
- `예상`, `확정`, `출금 완료`, `미확인` 상태 구분

기존 전역 Calendar와의 통합은 1차 범위에서 제외한다.

### 10.6 관리

한 화면 안의 작은 탭으로 나눈다.

```text
[계좌] [결제수단] [대출] [고정비]
```

- 계좌: 계산 잔액, 마지막 확인일, 잔액 맞추기
- 결제수단: 연결 계좌, 즉시 출금 여부, 카드 주기
- 신용카드: 사용 기간, 명세서 확정일, 출금 예정일, 출금 계좌
- 대출: 남은 원금, 기간, 월 납부 금액, 금리 메모, 다음 원금·이자, 다음 출금일
- 고정비: 예상 금액, 출금 계좌, 출금 예정일

### 10.7 통계

화면 상단에 기준을 항상 노출한다.

```text
[쓴 날 기준] [실제로 빠진 날 기준] [빠져나갈 예정 기준]
```

선택된 기준에 따라 모든 숫자와 차트를 함께 바꾼다. 한 차트 안에서 사용과 출금 기준을 섞지 않는다.

초기 차트는 세 개면 충분하다.

- 월 총액과 전월 비교
- 카테고리별 가로 막대
- 일별 누적 흐름

차트 라이브러리를 추가하지 않고 CSS와 작은 SVG를 사용한다. 같은 내용을 읽을 수 있는 표를 함께 제공한다.

## 11. 입력 흐름

입력 시작은 회계 용어 대신 아래 문장을 사용한다.

```text
썼어요 | 받았어요 | 옮겼어요 | 빌렸어요 | 갚았어요
```

### 11.1 일반 소비

1. 금액
2. 내용
3. 사용일
4. 결제수단
5. 카테고리

월 통계는 사용일의 월로 자동 적용하며 별도 월 선택 필드를 제공하지 않는다. 체크카드·현금·계좌 직접 결제는 실제 출금일을 사용일로 기본 입력하되 수정할 수 있다.

### 11.2 신용카드 사용

카드를 고르면 예상 청구 주기와 출금 예정일을 보여 준다.

```text
7월 쓴 돈 +48,000원
8월 14일 출금 예정 +48,000원
```

예상 날짜는 저장 전에 수정할 수 있고, 명세서가 확정되면 확정 금액과 차이를 보여 준다.

### 11.3 카드대금 실제 출금

1. 카드 명세서 선택
2. 포함된 사용·할부·환불 확인
3. 실제 출금 계좌, 날짜, 금액 입력
4. 차액이 0인지 확인
5. 출금 완료

카드대금 출금은 사용 통계에 다시 더하지 않는다.

### 11.4 대출 납부

총 출금액을 원금·이자·수수료로 나눈다. 세 금액의 합이 총액과 다르면 저장하지 않는다.

### 11.5 고정비

반복 규칙 저장 전에 앞으로 세 번의 결과를 미리 보여 준다.

```text
7월 통신비 → 8월 12일 출금 예정
8월 통신비 → 9월 12일 출금 예정
9월 통신비 → 10월 12일 출금 예정
```

특정 달의 실제 금액이나 출금일을 바꿔도 원래 반복 규칙은 유지한다.

## 12. 반응형·접근성

- 데스크톱은 기존 사이드바와 2열 콘텐츠를 사용
- 840px 이하에서 콘텐츠를 1열로 전환
- 600px 이하에서 5개 내부 탭은 한 줄 스크롤 또는 동일 기능의 네이티브 선택 상자로 제공
- 모바일 터치 영역 최소 44px
- 날짜는 네이티브 `input[type=date]`, 월은 `input[type=month]` 우선
- 금액은 우측 정렬과 tabular figures 사용
- 수입·출금은 색뿐 아니라 `+`, `−`, 텍스트를 함께 사용
- 예상·확정·완료는 색뿐 아니라 상태명과 아이콘을 함께 사용
- 달력·차트에는 읽을 수 있는 목록 또는 표 제공
- 키보드 포커스와 reduced-motion은 기존 규칙 재사용

## 13. 현재 저장소 통합 지점

현재 앱은 React/Vue가 아닌 순수 JavaScript SPA다. 새 앱을 만들지 않고 기존 렌더 흐름에 한 화면을 추가한다.

### 클라이언트

- `app.js`
  - `NAV_ITEMS`: `finance` 항목
  - 내비게이션 순서 정규화
  - `/finance` 초기 경로와 `popstate`
  - `renderView()`의 `renderFinance`
  - 가계부 전용 topbar/FAB 동작
  - 금융 상태 로드·로그인·저장
  - 입력, revision 조건부 저장, 충돌 시 최신 상태 재로딩
- `finance-model.js`
  - 계좌 잔액, 월별 사용·실제 입출금, 예정 금액, 카드 출금 예정일 계산
  - 브라우저 화면과 자동 검사가 같은 함수를 실행
- `styles.css`
  - 모든 새 스타일을 `.finance-view` 아래에 한정
  - 기존 토큰, 지표 그리드, 반응형 규칙 재사용

### 서버

- `server.js`
  - 금융 로그인·로그아웃·세션·상태 API 라우팅
  - 모든 금융 API에 인증과 별도 rate limit
- 작은 전용 저장 모듈 1개
  - `finance_state`, `finance_state_history`
  - revision read/write와 snapshot history
  - 금융 상태 검증

기존 `server/storage.js`의 공개 workspace 상태에는 금융 스키마를 추가하지 않는다.

### 테스트

- `/finance` 직접 접속·새로고침·뒤로가기
- 로그인되지 않은 금융 읽기·쓰기 `401`
- 로그인 rate limit과 로그아웃
- 신용카드 사용월과 실제 출금월 분리
- 카드대금 이중 집계 방지
- 고정비 예정일과 실제 출금일 분리
- 대출 원금·이자 분리
- 내부 이체 제외
- 할부 합계와 부분 환불
- 반복 규칙 중복 생성 방지
- revision 충돌 시 덮어쓰기 방지
- 저장 후 재접속 복원

핵심 계산은 작은 독립 테스트 파일 하나에 표 기반 사례로 검증하고, 경로·입력 흐름은 격리된 fixture 서버의 실제 Playwright 브라우저 시나리오로 검증한다.

## 15. 의도적으로 미룬 확장

- 계좌·카드·대출을 각각 완전한 SQL 테이블로 분리
